# QCU 2.0.0rc1 性能测评报告（vs 传统视觉 Computer Use）

> 测评日期：2026-09-16 · 机器：macOS darwin 25.2.0 (Apple Silicon, 3456×2234 Retina)
> 被测版本：qcu 2.0.0rc1（`Documents/QCU skill/.agents/skills/qcu`，Python 3.12.11 venv，daemon 常驻）
> 方法：全部为本机实测，独立 `QCU_HOME` + 一次性 Chromium profile（未触碰用户日常 profile 与真实业务数据）。
> 原始数据：本目录下 `web-separate.json` / `web-batch.json` / `vision-baseline.json` / `raw-playwright.json` / `desktop-ax.json`。

## 一句话结论

**是，明显快，但"快很多很多"要拆开说**：QCU 单步（观察+执行）实测 **75–195 ms**；
同一台机器上"截图流派"的**本地可测底线**（截图+PNG 编码+本地 OCR）为 **255–463 ms**，
且**还没算**上传网络与云端 VLM 推理（后者每步通常再加 1–3 s+，本次未测）。
本地可测部分 QCU 快 **3–6×**；按行业典型 VLM 延迟外推，整步差距在 **15–40×** 量级。
另外 QCU 交给模型的上下文是 **3.3 KB 结构化 JSON，约为全屏截图（3.3 MB PNG）的 1/1000**。

## 4. 加速比与开销分解

| 对比 | QCU | 对方 | 倍数 |
|---|---|---|---|
| 单步感知（web observe 74.5 ms vs 截+编+OCR 255–463 ms） | 74.5 ms | 255–463 ms | **3.4–6.2×** |
| 单步感知+执行（93 ms vs 含 VLM 的典型 1.5–4 s/步*） | 93 ms | 1500–4000 ms | **16–43×*** |
| 感知 payload（3.25 KB vs 3.34 MB） | 3.25 KB | 3.34 MB | **≈1/1000** |
| 整任务（batch 310 ms vs 视觉流派 15 步 ≈ 30–60 s*） | 310 ms | — | *外推，非实测 |

\* 带 * 的行含未实测的外推成分（云端 VLM 延迟按行业典型量级引用），下同，不作为实测结论。

QCU 每步 75–93 ms 的构成：**内部执行仅 10–26 ms，其余 ~50–70 ms 是 CLI 子进程 + RPC 开销**
（对比 1.6 时期 ~47 ms，基本持平）。对照裸 Playwright（整任务 38 ms）可知：
QCU 的主要剩余开销不是 a11y 读取，而是进程边界 —— 这正是 batch 模式存在的理由
（7 个动作 167 ms，把每步摊薄到 ~24 ms）。

## 5. 诚实边界

1. **未测云端 VLM**：本机无 API 调用，"15–40×"整步加速是外推；本地可严格实测的结论是 3–6×（感知阶段）。
2. **不含模型推理**：两组数字都不含 LLM 决策时间；但 QCU 喂给模型的结构化清单比截图 token 少约三个数量级，决策侧通常也更便宜更快。
3. **fixture 偏简单**（26 元素表单/58 元素 App）；重页面（如 HN 230 元素）历史数据 observe 213 ms，量级不变。
4. 视觉流派在 canvas/游戏等无 a11y 树场景仍是唯一选择，QCU 在此明确不支持（报错而非硬猜）。
5. 本机 OCR 数字（332 ms）比 1.6 时期记录（1149 ms）快，因屏幕内容不同；不影响量级结论。

## 6. 结论

**QCU 2.0.0rc1 的"快"在本地实测部分成立**：单步 75–195 ms、感知通道比"截图+OCR"底线快
3–6 倍、上下文体积小 ~1000 倍、定位确定性（20/20 web 断言 + 3/3 桌面 verified）。
叠加不可实测但公认的 VLM/网络环节后，整步差距在十几到几十倍量级——"快很多很多"
对 web/桌面 a11y 场景**成立**；对 canvas/游戏场景**不适用**；剩余优化空间主要在
CLI 进程开销（~50–70 ms/条），batch 模式已把它摊薄。
